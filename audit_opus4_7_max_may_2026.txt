## [MODULE 1] LP MECHANICS AUDIT

### A. Stratégie de quoting

| Aspect | Implémentation | Verdict |
|---|---|---|
| Mid-price source | WebSocket prioritaire (`main.py:102-109`) avec fallback REST batch (`get_midpoints`) puis appels individuels | OK — design dual hot/cold solide |
| Calcul du spread | Mode tick-based : `offset = QUOTE_OFFSET_TICKS * tick` (`core/quoter.py:185-195`) avec auto-élargissement adverse-fill (`fph > ADVERSE_FILL_RATE_THRESHOLD → +1 tick`). Fallback legacy : `max_spread * tightness_factor` | Correct mais **simpliste** |
| Skew adjustment | 4 paliers : alert 25% → action 30% → recovery 45% → hard pause 70% (`core/inventory.py:248-285`). Côté lourd : `bid_offset += skew_widen` (`quoter.py:232-240`) | Bien calibré |
| Order sizing | `min_size * SIZE_MULTIPLIER`, capé par `allocated_capital / 2` par côté (`quoter.py:262-278`). ASK strict ≤ position détenue (`quoter.py:275-278`) | Conservateur — capital efficiency moyenne |
| Refresh logic | **Hybride event-driven + cycle** : hot path WS `hot_requote()` (`main.py:185-238`) avec debounce 1s ; cold path 10s (`REBALANCE_INTERVAL_SECONDS=10`) | Très sophistiqué pour un OSS bot |
| Cancellation | Smart-diff : ne replace que si `price_moved > ORDER_UPDATE_THRESHOLD_TICKS * 0.01`, `size_changed > 10%`, ou `age > MAX_ORDER_AGE_SECONDS` (`order_manager.py:282-294`) | Excellent — preserve scoring uptime |

### B. Couverture des marchés

| Filtre (`config/markets_filter.py:57-94`) | Valeur |
|---|---|
| `MIN_END_DATE_DAYS` | 120 jours |
| `MAX_24H_VOLUME` | $800k (évite marchés où les pros dominent) |
| `MIN_24H_VOLUME` | $500 |
| `MIDPOINT_MIN/MAX` | 0.15 – 0.85 |
| `MIN_REWARD_RATE_DAILY` | $5/jour |
| Scoring composite | reward_rate × volume_sweet_spot × longevity_bonus × tag_bonus × capital_eff (`markets_filter.py:122-169`) |
| Multi-market parallèle | `MAX_MARKETS=60` (default) / `MAX_MARKETS_PER_CYCLE=20` avec round-robin top-15 toujours servi (`main.py:57-83`) |
| Gestion near-resolution | **Filtre statique uniquement à la sélection** — aucun garde-fou continu si un marché passe de 0.50 à 0.92 in-flight |

**Faiblesse critique** : `markets_filter.py:72` rejette mid hors [0.15, 0.85] *au moment de la sélection* mais aucune relecture en boucle. Un marché peut dériver dans la zone toxique sans être délisté. → ANALYSIS.md le reconnaît déjà ligne 121.

### D. Gestion des fills

| Cas | Comportement |
|---|---|
| Partial fill | `FillEvent.filled_size` = `trade.size` (réelle), pas `order.size` original (`fill_collector.py:97-127`). Correct depuis fix P2-3 |
| Adverse fill | Trigger force-replace (`force=market.condition_id in filled_cids`, `main.py:433`) + cumul `_fill_rates` pour widening |
| Max position per market | Implicite via `MAX_CAPITAL_PER_MARKET` ($80 dans le `.env` actuel) + `SKEW_HARD_PAUSE_THRESHOLD` |
| Rebalancing après skew | Recovery mode réduit ASK (`SKEW_RECOVERY_ASK_SIZE_PCT=0.50`) côté lourd ; widen BID (`skew_widen = base_offset * skew_ratio * 1.4`) |

### Verdict Module 1

**Ce n'est PAS un order spammer**. C'est un *vrai* market maker amateur-pro :
- Smart-diff évite churn inutile → preserve quote uptime (CRITIQUE pour scoring quadratique)
- WS hot path réagit en ~1s aux moves
- Skew management 4-tier protège du drift directionnel

**MAIS** : aucune intelligence d'adverse selection (toxicity scoring, VPIN, lambda), aucun garde-fou résolution continu. C'est un **market-making naïf calibré pour fuir le danger** plutôt que pour le détecter activement.

**Score LP mechanics : 7/10**

## [MODULE 3] ROI & BACKTEST ASSESSMENT

### A. Modèle P&L du code

**Revenus modélisés** :
- LP rewards : pool fetché via Gamma `/markets`, **divisé arbitrairement par 10** (`rewards_tracker.py:274`) — *aucune* mesure réelle de la part user
- Realised PnL : average-cost basis correct (`inventory.py:217-227`) mais ignore les fills de seed mal valorisés

**Coûts non comptabilisés** :
- Gas Polygon : ignoré (~$0 par order signé EIP-712 ; ~$0.50 par cycle d'allowance approval, mais one-shot)
- Adverse selection : non quantifié — uniquement compteur grossier `_fill_rates` (`quoter.py:188-194`)
- Spread cost : non mesuré (BID-ASK roundtrip si rebalance manuel)
- **Cost basis bug** : `main.py:866-876` initialise `pos.yes_cost = bal * mid` quand un balance on-chain existe, mais le seeder a acheté à `mid + SEED_AGGRESSIVE_TICKS * tick` (typiquement +3 ticks) → cost basis sous-estimé → realised PnL surestimé

### B. Adverse selection risk

| Mécanisme défensif présent | Limites |
|---|---|
| `_fill_rates` widening (>3 fills/h → +1 tick, >9/h → +2) | Réactif, pas prédictif |
| Velocity guard WS (3 ticks dans 5s) | Bon mais ne cible pas le sens directionnel adverse |
| Skew management | Limite l'exposition mais n'identifie pas la *toxicity* du flow |
| Force-replace après fill | Évite la double-fill au même prix |

**Ce qui manque** :
- Aucune analyse fill vs mid futur (5s, 30s, 5min)
- Aucune corrélation cross-market
- Aucun event calendar (élections, FOMC dates)
- Aucun arrêt automatique si midpoint sort de [0.20, 0.80] *en cours de vie*

**Conséquence** : un trader informé peut systématiquement picker les ordres BID quand il sait que le marché va baisser. Le bot le détecte *après* coup via `_fill_rates` mais a déjà perdu.

### C. Simulation

**Aucune donnée historique disponible** dans le repo (`logs/` est gitignored et vide via `.gitkeep`).
**Aucun framework de backtest** (`backtest/` n'existe pas).

→ Tout le tuning (`TIGHTNESS_FACTOR_SAFE=0.48`, `QUOTE_OFFSET_TICKS=1`, `SKEW_*` thresholds) est **arbitraire**. Aucune preuve empirique que ces paramètres optimisent quoi que ce soit.

### D. Stress test

| Scénario | Comportement |
|---|---|
| Marché résout à 0 alors que bot long YES | Aucune protection — perte = `yes_size * yes_avg_cost`. Le filtre `MIN_END_DATE_DAYS=120` ne suffit pas si le marché bouge fort. |
| Drawdown journalier | **Aucun circuit breaker P&L** — seulement circuit breaker *par marché* sur erreurs API (`order_manager.py:686-706`) |
| Marché suspendu mid-position | Position bloquée, watermark ne progresse plus, ASK orders peuvent rester pendants |
| Crash process | `cancel_all_orders` au shutdown OK ; au restart `cancel_all` au startup (`main.py:815`). Watermark trades persisté → fills reconciliés |

### Estimation APY (capital $10k baseline)

| Scénario | LP rewards/mois | Adverse selection | Net mensuel | APY |
|---|---|---|---|---|
| Best case (top 5% scoring, low vol) | $600-800 | $50-100 | $500-750 | 60-90% |

**Verdict P&L : BREAKEVEN à PROFITABLE en base case, MAIS variance énorme — un seul résolution event peut effacer 2-3 mois de gains.**
